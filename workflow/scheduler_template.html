Tracker Cost plan

Simulation tracker

The simulation tracker is updated by running workflow/nird_progress.py in the noresm_cmip7_simulations repository.
It is run on NIRD from the clone in /projects/NS9560K/www/diagnostics/noresm/noresm_cmip7_simulations.
The script uses information from the GitHub issues, the run scripts on GitHub that go with the issues, the case directories on NIRD and the CMORization directories:

  • The GitHub issues determine each case's labels, assignee and CMOR data version.
  • The run scripts on the CMIP7_Runscripts branch determine how each case started and which case it continues or branches from.
  • The case directories on NIRD determine each case's latest model date, its cost and throughput, and the size of its history and restart output.
  • The CMORization directories of cmip7-prep and cmor4cmip7 determine the years each tool has CMORized and the size of the time series and CMOR output.
Run nird_progress.py

To update the tables, run it from that directory:

cd /projects/NS9560K/www/diagnostics/noresm/noresm_cmip7_simulations
git pull
python3 -I workflow/nird_progress.py

The script finds each case's directory, /nird/datalake/NS9560K/noresm3/cases/<case>, from its issue title, and writes progress.json next to this page. Its options are needed only for output somewhere else; python3 -I workflow/nird_progress.py --help lists them.

Workflow steps
  • Determine the case name

    A case is named compset.resolution.version.issue.date, for example n1850Gaxg.LM.nor30b22.502.20260801:

    • compset: see column M of the NorESM3 CMIP7 experiments spreadsheet;
    • resolution: LM for ne16pg3_tn14, MM for ne30pg3_tn14;
    • version: nor30 for noresm3_0_, followed by the beta, e.g. b22 for beta22;
    • issue: the number the case's GitHub issue will have;
    • date: the date the case is made, as YYYYMMDD.
    Make the experiment's GitHub issue

    Issues go in NorESMhub/noresm_cmip7_simulations, one per case. The tracker is filled in from them, so:

    • title: the case name and nothing else;
    • experiment label: the CMIP7 experiment, e.g. esm-hist, spelt as in the tracker;
    • variant label: the ensemble member, e.g. r1i1p1f1;
    • assignee: whoever runs it, shown as the run's owner;
    • completed: add this label when the run has finished;
    • test: add this label to a case that is not a CMIP7 run, to leave it out;
    • esgf: add this label when the data is on ESGF;
    • description: three entries. - cmor data version: has TBD until the version is decided, which is before CMORization starts, then the version: v and its date as YYYYMMDD, the v optional. The two output roots are default unless the output is somewhere else:
    - cmor data version: v20261028
- cmip7prep output root: default
- cmor4cmip7 output root: default

    The CMOR data version, e.g. v20261028, must agree between the two CMORization tools for a given span of years: cmip7-prep, which CMORizes the atmosphere, land, sea ice and land ice (its --data-version), and cmor4cmip7, which CMORizes the ocean and ocean biogeochemistry. That way all the realms for those years are one edition of the dataset.

    If the version directories on NIRD don't match the issue, or each other, the case's chip in the cmip7prep or cmor4cmip7 column, its issue and years such as #002 1–170, is red. Click the chip to see the case's output directory, the versions, and what disagrees.

    The progress script finds everything else itself: each tool's output in its default place, explained under cmip7-prep and cmor4cmip7 in CMORize, and the case's run script by the issue number its name starts with (see Archive the run script).

    • continuing a simulation in a new case: give the new issue the same experiment and variant labels. Its run script's RUN_REFCASE is the earlier case. The tracker reads the two as one simulation and takes its progress from the later model date, as with #2 and #11;
    • another member of the ensemble: give it its own variant, e.g. r2i1p1f1. The run's years done are the mean over its members.
    Archive the run script

    Push the case's run script straight to its directory under scripts/ on the CMIP7_Runscripts branch; this needs write access to the repository.

    • directory: scripts/<MIP>/<experiment>/. A case that is not a CMIP7 run, whose issue has the test label, goes in scripts/test/;
    • name: issue.experiment.resolution.beta.variant.date.sh. The progress script finds the case's script by the issue number it starts with, so no other script may start with it:
      • the experiment and variant from the issue's labels, the rest from the case name, e.g. 011.piControl.LM.beta28.r1i1p1f1.20261102.sh for n1850GHGGaxg.LM.nor30b28.011.20261102;
    • push: in a clone of the repository,
      • git switch CMIP7_Runscripts and git pull;
      • copy the script into its directory under its name;
      • git add the script;
      • git commit with the message:
        • Run script for #<case issue>, e.g. Run script for #11. Naming the issue makes GitHub list the commit on it. Don't use Closes #11 or Fixes #11, as those close the issue;
      • git push;
    • tracker: after the next run of the progress script, the tracker links the script after the case's issue, as sh.
  • How the run is done and tracked

    The progress script reads the run's Status and Progress on NIRD.

    Create and build the case. On Olivia and Betzy, cases go in /cluster/projects/nn9560k/$USER, each in a directory named after the case: /cluster/projects/nn9560k/$USER/<case>.

    Set the run's priority and coordinate it with the other runs. Copy the output to NIRD by hand with rsync while the run is going. The progress script reads the years done from the atmosphere history files copied there, and the tracker shows them in the Progress column and sets the Status to In progress. To set it to Completed, add the completed label to its issue.

    To decide:
    • how often to write restarts (every 5 or 10 years?);
    • how to log what was run (code version and settings);
    • whether the case directory is archived on NIRD too;
    • which files are removed (for example intermediate restart files).
The CMORization steps
  • Make the CMORization issue

    Once the simulation has finished, open an issue in NorESMhub/CMIP7_CMOR-Publish from its template, which is like the CMIP6 one, and label it cmorization. The repository's other labels are publication, archive, cmor_bug, publication_bug and retract.

    Before either tool starts, set the CMOR data version in the description of the case's issue in noresm_cmip7_simulations. Both tools write the case's years into that version, cmip7-prep with --data-version:

    - cmor data version: v20261028
- cmip7prep output root: default
- cmor4cmip7 output root: default

    The progress script reads each tool's progress in its default place, as the two steps below explain, and the tracker shows where when you hover the cmip7prep or cmor4cmip7 column. Output somewhere else needs its directory in place of default in the issue's - cmip7prep output root: or - cmor4cmip7 output root:. The directory may have <case>, <resolution>, <experiment> and <variant> in it, which the script fills in from the issue, e.g. /nird/datalake/NS9560K/someone/<case>.cmor.

    To decide: how urgency is shown.
  • CMORize the atmosphere, land, sea ice and land ice using cmip7-prep

    The CMORized output goes in /nird/datalake/NS9560K/noresm3/cases/$CASE.cmor for now, and will later go in /nird/datapeak/NS9034K with the cmor4cmip7 output. The progress script reads the completed_steps_*.json files cmip7-prep writes there, and the tracker shows the years CMORized so far, e.g. 1–50.

    The script reads only the case's .cmor directory, not the ones below it. Each case has its own, with its own time series and logs. For output elsewhere, the cmip7prep output root entry gives the directory that holds the case's completed_steps_*.json files.

    The tracker shows the cmip7prep years case by case, a chip for each case with CMORized years, since each case has its own directory: piControl's #2 can be done while #11 is not.

  • CMORize the ocean and ocean biogeochemistry using cmor4cmip7

    The CMORized output goes in /nird/datapeak/NS9034K/.CMIP7, under the model, experiment, variant and version, e.g. NorESM3-LM/piControl/r1i1p1f1/v20261028. The first 100 years of piControl's ocean are being CMORized there now. The progress script reads the time ranges in the names of the files there, e.g. _000101-001012.nc, and the tracker shows the years every variable has, e.g. 1–10.

    The script reads the simulation's variant directory, named from the issue's resolution, experiment and variant, e.g. /nird/datapeak/NS9034K/.CMIP7/NorESM3-LM/piControl/r1i1p1f1, and every version below it, so a later version is read too. It takes the files whose names have the issue's experiment and variant, e.g. _piControl_r1i1p1f1_. These hold all the simulation's years, so the tracker counts each year once however many issues the simulation has. For output elsewhere, the cmor4cmip7 output root entry gives the variant directory; a root above the model directory would mix the LM and MM files of the same experiment and variant.

cmip7-prep and cmor4cmip7 lay out their output differently. That doesn't matter for publication: esg-prep links both into the structure ESGF needs. The CMORization and publication workflow, and the esg-prep command, will be added here as they are settled.

  • Publish the data on ESGF label: esgf

    The ESGF column depends on the label esgf: it shows ✓ once the case's issue has it, after the next run of the progress script. Add the label when the data is published.

Cost table

The full planned cost of each run, a table for each MIP at each resolution; progress is tracked on the Tracker page. The runs, their members and their years are the plan the page is built with, and the runs not in it for now are listed at the bottom. Core-hours are members × years × cost per simulated year, on the machine the run runs on: Betzy for a run whose timing files say so, Olivia otherwise. A run with timing files of its own is costed with them; any other run with its configuration's value, the mean over that configuration's runs that have timing files, or an earlier timing if none has. Days per member is how long one member takes on its own.

The four TB columns are the output each run will leave on NIRD once all its members and years are done, not what is there now: members × years × the GB per simulated year its cases have on NIRD so far, measured by the progress script. History is the model's history files, restarts the restart sets as kept, time series cmip7-prep's time series, which are to be deleted, and CMOR the CMORized files of both tools. A run with no output of its own takes its configuration's, in grey; hover a value for the GB per simulated year and its parts.
